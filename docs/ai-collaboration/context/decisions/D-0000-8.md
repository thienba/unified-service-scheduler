Data storage, with the backend mocked: **seed data in JSON files** in the repo (branches, hours, technicians and skills, shifts, bays, courtesy cars, service types, customers and vehicles); **runtime data in IndexedDB** (the browser's database, used through the Dexie library), loaded from the seed on first start, so appointments, the manager's edits and the outbox survive a reload. The scheduling module reaches data only through a **repository interface**: an in-memory implementation for tests, an IndexedDB one for the app, and a PostgreSQL one described in the System Design Document (with an exclusion constraint per bay and technician). The confirm re-checks availability and writes inside one IndexedDB read-write transaction, so two tabs confirming the same slot give exactly one winner (REQ-BOOK-009). Rejected: localStorage (no transactions across tabs), json-server (an extra server, rules not in it), PGlite (heavier, riskier). Reason: the human chose option A of the proposal ("A"), (the human's original message is kept in the private work repo).
