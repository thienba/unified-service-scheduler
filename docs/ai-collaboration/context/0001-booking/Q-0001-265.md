**Question:** React Aria's Select keeps a hidden native `<select>` inside the page for autofill and forms. It cannot be turned off: `react-aria-components` 1.22.1 renders it for every list of up to 300 options, and our TimeField (96 options) is a Select too. It is hidden from sight and from screen readers and has no tab stop, so no native drop-down is ever seen or used. But WebKit still prints its "Refused to apply a stylesheet" message once for every `<select>` element under our policy, hidden or not (checked in WebKit 27.2: a hidden `<select>` alone on a page under our policy prints it). So the WebKit allowance of D-0001-109 is still needed by the policy checks. What should we do?

- A. Keep the allowance (`tests/e2e/policy-support.ts` and its callers stay as they are). The only cost is the known WebKit console line; nothing the page needs is blocked, and no native control is visible.
- B. Build our Select without React Aria's `Select` part: a React Aria `Button`, `Popover` and `ListBox` with our own open state. No `<select>` at all, so the allowance can go. But we would rebuild the select keyboard (typing on the closed button, arrows to open, the right ARIA attributes) that React Aria was chosen to give us, and test it ourselves.
- C. Wait for React Aria to offer a way to leave the hidden `<select>` out, and keep the allowance until then.

**Recommendation:** A (with C as a later check). The ticket's goal, no browser drop-down in sight, holds; only a console line in WebKit remains, and B takes on the accessibility work D-0001-131 chose React Aria to avoid.

**Built as:** A. The allowance stays and is still exercised by `tests/e2e/policy-support.spec.ts`. The ticket's criterion "the WebKit `<select>` allowance is removed" is therefore not met; this question asks you to accept that or to choose B.
