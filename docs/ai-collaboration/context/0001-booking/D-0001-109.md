**Question:** WebKit prints "Refused to apply a stylesheet because its hash, its nonce, or 'unsafe-inline' appears in neither the style-src directive nor the default-src directive" once for every native `<select>` element on a page. It comes from WebKit itself, not from our code or a package: a page that holds only a bare `<select>` and our policy does the same (WebKit 27.2 in Playwright 1.64.1), while Firefox and Chromium print nothing. One small piece of styling is lost: our select boxes ask for "..." when the chosen option is too long (`truncate` in `src/ui/components/Fields.tsx`), and WebKit applies that through the blocked style, so in WebKit a long option is cut off hard instead (the car box shows "Demo Motors Hatch, AB00 DMA" cut through the last letter instead of "Demo Motors Hatch, AB00 D..."). Our own stylesheet cannot reach that part of the control. Every other screenshot of the select pages is the same pixel for pixel with and without the policy (evidence in the ticket's shots/). Our code cannot stop it without loosening the policy or dropping the native control. What should the policy checks (SEC-15.AC-3, SEC-11.AC-3) do with it?

- A. Accept it as a known WebKit message. The tests record every policy violation event with the element it was raised on; in WebKit only, a style violation raised on a `<select>` element and its exact console line are set aside, and every other violation or policy message still fails the test in every browser. The System Design Document's list of unverified claims (security.md section 7, assumption 5) gets a line saying the message is WebKit's own and was not checked in real Safari.
- B. Replace every native `<select>` with our own list box built from buttons and a list. The message goes away, but we lose the native control's keyboard, screen reader and phone picker behaviour and take on a large accessibility job (NFR-4).
- C. Add `style-src 'self' 'unsafe-inline'` (or a hash of WebKit's internal style, which we cannot read and which may change with any WebKit release). The ticket and SEC-15 forbid 'unsafe-inline'; a hash would be fragile.

**Decided:** the recommended option. The recommendation was: A. Nothing is blocked that the page needs (the full choice is still read out and shown in the booking summary; only the "..." is missing in WebKit), the check stays strict for everything else, and the native control keeps its accessibility. Choose B only if a clean Safari console matters more than the native control; C loosens the policy. The ticket is built as A until you answer (`tests/e2e/policy-support.ts`, used by `tests/e2e/whole-app.spec.ts` and the SEC-15.AC-1 test in `tests/e2e/schedule.spec.ts`). The line in security.md section 7 is not written yet: this ticket may only edit the Q- file in the work repo, so the lead adds it when A is chosen. The line goes into context/security.md (assumption 5) and the System Design Document's list of known limits: WebKit prints one "Refused to apply a stylesheet" message per native <select> under style-src 'self'; it comes from WebKit itself; the only visible effect is that a long option is cut at the edge instead of ending in "...".

Reason: the human's answer ("Ok theo recommend"), (the human's original message is kept in the private work repo).
