**Question:** Should a time be held for the customer while they fill in the booking form, so another person cannot take it first?

- A. No hold, as built: the first confirm the server accepts wins; the other gets the apology with the closest times.
- B. A soft hold: choosing a time holds it on the server for about 5 minutes with a countdown; others see it as busy; it is released on timeout or when the customer leaves. The race moves to the hold step, abandoned holds block other customers, one hold per person is needed, and it needs new API calls, expiry, a countdown and new tests (one or two tickets).
- C. No hold, but warn early: when a time is chosen, and every 30 seconds while it stays chosen, the page checks it again with the existing availability check; if it has just been taken, the page says so at once (before Confirm) and offers the closest times.

**Decided:** C. B is written in the System Design Document as a considered extension (when it would be worth it: long forms or payment; and its costs). The first confirm still wins (REQ-BOOK-009); C only tells the customer sooner.
