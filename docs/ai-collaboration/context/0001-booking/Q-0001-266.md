**Question:** React Aria adds two small inline `<style>` elements of its own, which our policy (`style-src 'self'`, no 'unsafe-inline') refuses:

1. On every page with a React Aria button: `[data-react-aria-pressable] { touch-action: pan-x pan-y pinch-zoom }`. React Aria skips it when an element with the id `react-aria-pressable-style` is already in the page. The build puts an empty `<meta id="react-aria-pressable-style">` in `index.html` and the same rule in `src/styles/app.css`, so nothing is refused and nothing is lost. Checked in Chromium, Firefox and WebKit.
2. On an iPhone or iPad only, while a popup is open: `* { overscroll-behavior: contain }` (stops the page behind a sheet from scrolling when a list reaches its end). It has no id to take. Playwright's WebKit does not run this path, so it was not seen in the tests; on a real iPhone the policy would refuse it, print one console message, and the page behind may move a little when a list is scrolled past its end.

What should we do about the second one?

- A. Accept it as a known limit on iPhones and iPads, written in security.md's list of unverified claims (it was not checked on a real device).
- B. Add the hash of that exact style to `style-src` (`'sha256-...'` of the text React Aria writes). Exact, but the hash breaks when React Aria changes the text, and it loosens the policy by one style.
- C. Put `overscroll-behavior: contain` on our own sheet's scrolling area in `app.css`. This covers our sheets; React Aria's style would still be refused and its console message would still print.

**Recommendation:** C, and write A's line too. Our sheet then behaves right on an iPhone, the policy stays strict, and the remaining console line is known.

**Built as:** point 1 is done as described. For point 2 the build does C (`overscroll-behavior: contain` on `.ctl-sheet-body` and `.lb`) and nothing more; the line for security.md is for the lead to add (this ticket may only write Q- files in the work repo).
